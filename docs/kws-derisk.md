# How many bytes of DSP does a keyword spotter need? A half-day measurement

CIFAR-10 gets its input transform for free. An 8x8 RGB block mean is one reshape
and one `.mean()`, about thirty source bytes, and it stores nothing — which is
why this repo's sub-kilobyte frontier can spend almost its whole budget on the
classifier. Audio has no obvious equivalent. A log-mel front end needs framing,
a window, an FFT, a filterbank and a log, and the filterbank in particular is a
matrix, which in this repo's accounting is *weight*, not code.

That is the question this memo answers, on Speech Commands v2, 12-class
keyword spotting. It also asks the two that follow from it: does anything
classify at a kilobyte, and does any artifact pay for its own transmission.

Every number below is MEASURED on this box by a named script in this repo, or
VERIFIED against a URL that was actually fetched. Nothing is asserted from
memory. Configurations were chosen on the dataset's own validation list; test
was scored once per declared point.

**Recommendation: NO-GO as a project, and the measurement is the deliverable.**
Reasoning in the last section. Neither kill criterion fired.

---

## The answer, first

**A complete log-mel front end costs 99 bytes.** Not 99 bytes of weights — 99
bytes of *artifact*, measured through the harness, over the cost of a Python
file that computes nothing. It stores no coefficients at all. The same front end
with the filterbank shipped as data instead of generated by a formula costs
**1,119 bytes**, an eleven-fold difference, and it is the only row in the table
that fires the kill criterion.

Two facts make it cheap, and both are worth stating because neither was obvious
before it was measured:

* **The FFT is already in the declared runtime.** `np.fft.rfft` is numpy, so its
  twiddle factors live in the interpreter the artifact is allowed to assume, not
  in the artifact. The single most expensive-looking part of an audio front end
  is free.
* **Mel spacing is a formula, so the filterbank is generatable.** This is lever C
  from [what-to-try.md](what-to-try.md) — *anything a line of numpy generates
  costs nothing* — and it is worth 1,020 B here, which at a kilobyte budget is
  the difference between the band existing and not existing.

So the sub-kilobyte band on Speech Commands is not closed by DSP. It is a real
band, it has no published occupant, and the front end is not what stops you
entering it. We entered it: **41.00% at 1,024 B and 17.16% at 436 B**, on the
official 4,890-utterance test set, from artifacts that run in the harness.

What stops this being a project is elsewhere, and it is two things. The
closed-form family is forty points behind the published literature at comparable
size — an inversion of the CIFAR position, where it is fifteen points ahead. And
the MDL board, the scoreboard that makes the sub-kilobyte band matter rather
than merely exist, is short by 27 to 30 accuracy points uniformly across the
whole frontier.

## Kill criterion 1 — the cost of a usable front end. DID NOT FIRE.

*If a minimal usable feature extractor cannot be written in under ~250 B of
golfed numpy, the sub-KB band does not exist here.*

`experiments/kws_extractors.py`. Each row is a **complete runnable artifact**:
it computes its features and returns a label. The classifier is deliberately
degenerate — `v.argmax(1) % 12` — so `bytes` is the floor, what the front end
costs before any model exists. `delta` subtracts the `null` row, which is the
same artifact with the DSP removed, and so isolates the DSP from the fixed cost
of being a Python artifact at all. Every row was run through the harness
sandbox on real waveforms, so a fragment that does not execute cannot post a
byte count.

| extractor | bytes | delta | src B | coef B | dims | stored? | what it is |
|---|---:|---:|---:|---:|---:|---|---|
| `null` | 88 | +0 | 73 | 0 | 12 | no | no DSP at all |
| `sub64` | 109 | +21 | 94 | 0 | 64 | no | raw waveform block-averaged to 64 samples |
| `env64` | 117 | +29 | 102 | 0 | 64 | no | rectified envelope, 64 frames |
| `env32x1` | 125 | +37 | 112 | 0 | 32 | no | log rectified envelope, 32 frames |
| `fft-spec` | 129 | +41 | 126 | 0 | 8,032 | no | full rfft magnitude spectrogram |
| `zcr32` | 155 | +67 | 156 | 0 | 64 | no | zero-crossing rate + envelope |
| `fft-oct` | 173 | +85 | 195 | 0 | 640 | no | rfft into 20 octave-spaced bands, log |
| `fft-mel` | **187** | **+99** | 212 | 0 | 640 | no | **rfft into 20 true-mel bands, log — edges from the formula** |
| `mfcc` | 199 | +111 | 239 | 0 | 320 | no | fft-mel then a DCT-by-rfft cepstrum |
| `fft-mel-han` | 205 | +117 | 241 | 0 | 640 | no | fft-mel with a Hann window, generated by `cos()` |
| `haar` | 207 | +119 | 244 | 0 | 279 | no | Haar packet, dyadic bands, no trig table |
| `fft-mel-stored` | 211 | +123 | 222 | 20 | 640 | YES | fft-mel with the 20 band edges shipped as bytes |
| `mel-matrix` | **1,207** | **+1,119** | 219 | 10,040 | 640 | YES | **the textbook front end: a real 20x251 triangular filterbank, shipped** |

Nothing usable costs 250 B. The most elaborate front end in the table — mel
bands, a Hann window, a log — is 117 B over null, and a cepstrum on top of it is
111 B. The criterion does not fire, and it does not come close.

Three things the table settles:

**The filterbank matrix does not have to be weight.** `mel-matrix` is the same
features as `fft-mel`; the only difference is that its 20x251 triangular
filterbank arrives as 10,040 bytes of float16 rather than from
`(21.9*10**np.linspace(0,1.094,20)-21.9).astype(int)`. It compresses well — xz
takes the whole artifact to 1,207 B — and that is still 6.5 times `fft-mel`'s
187 B, and **55% of the entire 2,191 B label budget this dataset has to beat,
spent on a filterbank before a single weight is shipped**. Generating the bands
rather than storing them is not an optimization here; it is the difference
between a sub-KB artifact and no sub-KB artifact.

**Even shipping just the twenty band *edges* loses.** `fft-mel-stored` is 24 B
worse than `fft-mel`, because twenty uint8s in a weight file cost more than the
formula that produces them, and source is discounted by xz
while near-random bytes are not. The asymmetry the CIFAR work found in
[what-to-try.md](what-to-try.md) holds here.

**A trig-free transform is not needed and does not help.** `haar` was included
because a Haar/Walsh packet needs no table at all, which looked like the safe
route if the FFT turned out to be expensive. It is the *second most expensive*
row that stores nothing, at +119 B, because the butterfly loop costs more source
than `np.fft.rfft` costs anything. There is no reason to avoid the FFT.

### Was this table capable of a negative?

A criterion that nothing can fail is not a criterion. `mel-matrix` is in the
table for exactly this reason: it is the front end an off-the-shelf pipeline
would ship, and it fires the criterion at +1,119 B. The script refuses to print
a verdict if no row fires — if every row passes, the table has not been shown
capable of a negative and it raises rather than reporting a clean bill.

## Kill criterion 2 — does anything classify at a kilobyte. DID NOT FIRE.

*If a ~1 KB artifact cannot beat chance (8.33%) by a wide margin, no-go.*

The best artifact at or under 1,100 B scores **41.00% on the 4,890-utterance
official test set**, at 1,024 B — 4.9x chance, 46 standard errors clear of it
(SE 0.70 pp at n = 4,890). Even the 436 B floor scores 17.16%, twice chance. The
criterion does not fire, and it does not come close.

For scale, this repo's CIFAR-10 artifact at 931 B scores 43.79% against a 10%
chance line, which is 4.4x. **At about a kilobyte you buy roughly four to five
times chance, and it appears not to matter much whether the input is an image or
a second of speech.** That is the most transferable number this measurement
produced, and it is why the rest of the memo reads the way it does: very little
here is surprising once you have the CIFAR curve.

(The CIFAR figure predates this repo's validation split and was chosen on test,
which inflates it by perhaps a point; the Speech Commands figures were not. The
comparison is loose in the direction of flattering CIFAR.)

## Method

### Data, splits and license

Speech Commands v2, the release tarball from
`http://download.tensorflow.org/data/speech_commands_v0.02.tar.gz`
(2,428,923,189 B, MEASURED). **CC-BY-4.0**, verified three ways: the `LICENSE`
file inside the tarball is the full CC Attribution 4.0 International text; the
tarball's own `README.md` says "It's licensed under the Creative Commons BY 4.0
license"; and Warden's dataset paper
([arXiv:1804.03209](https://arxiv.org/pdf/1804.03209), §2) says "this dataset has
been released under the Creative Commons BY 4.0 license". No gate, no scraping,
no mirror of unclear provenance.

The 12-class setup is the standard one: ten target words plus `_silence_` and
`_unknown_`. **Split membership is the dataset's own**, from the
`validation_list.txt` and `testing_list.txt` files inside the tarball, which are
a speaker-disjoint hash split. Nothing in this repo re-splits and nothing
selects on test.

`experiments/kws_prep.py`, MEASURED:

| split | total | target words | `_unknown_` | `_silence_` |
|---|---:|---:|---:|---:|
| train | 36,923 | 30,769 | 3,077 | 3,077 |
| val | 4,445 | 3,703 | 371 | 371 |
| **test** | **4,890** | 4,074 | 408 | 408 |

The test figure is the canonical one and it is not a coincidence of my
arithmetic. It reproduces because the 10%/10% unknown-and-silence convention is
Google's own from `input_data.py`. Independently confirmed: the companion
archive `speech_commands_test_set_v0.02.tar.gz` contains exactly 4,890 wav
files in 12 directories, TFDS lists `'test': 4,890` with `num_classes=12`, and
`mlcommons/tiny`'s `kws_util.py` carries `# 4890` as its test-set comment.

Two choices the released lists do not determine, stated rather than buried.
Which unknowns and what the silence waveforms are is settled by a fixed seed.
And the six `_background_noise_` recordings, which Google's code shares across
splits, are here cut into three contiguous regions with each split drawing only
from its own — a deviation, in the conservative direction, so that no model can
recognise a particular stretch of dishwasher noise it saw in training.

Train and validation counts are pipeline-dependent across the ecosystem (HF
gives 84,848/9,982, TFDS 85,511/10,102) because they differ in how many silence
clips they synthesize. Only **test = 4,890 is stable across every source**, and
that is the only one any number here is scored on.

### The artifacts

Waveforms reach `predict()` as int16 `[N, 16000]` — one second at 16 kHz, the
dataset's own nominal format, padded or truncated. Everything else is the
harness unchanged: numpy only, self-contained, re-run from its own serialized
bytes in a sandboxed fresh subprocess, with the audit hook and the
batch-composition probe. Scoring goes through `tinycifar/evaluate_nclass.py`,
which imports `evaluate._DRIVER` rather than copying it, exactly as the
class-scaling work did. **No CIFAR file was modified**; `python3 -m pytest tests -q`
is 64 passed (43 before, plus 21 new) and `ruff check` is clean.

**The trainer and the artifact share one source string.** The feature expression
is `exec`'d by the trainer and pasted verbatim into `predict.py`. There is no
second implementation to keep in sync, so trainer/artifact drift — the failure
mode that would silently inflate every accuracy here — is designed out rather
than tested for.

### Selection

`(front end, frames, bands, bits)` is the size axis and is **declared**: every
point is scored on test, so the tables are measurements and not a best-of-N.
Only the ridge penalty is chosen, and it is chosen on the validation split
through the *real quantized artifact* — ranking penalties on the float head
picks the wrong one at low bit widths. The random-filter seed is fixed at 0 and
never searched.

### Reproducing

```bash
python3 experiments/kws_prep.py --out data/sc12.npz
python3 experiments/kws_extractors.py
python3 experiments/kws_ceiling.py
python3 experiments/kws_ridge.py --out /tmp/kws_ridge \
    --kinds mel oct --frames 16 32 49 --bands 8 10 12 16 20 --bits 1 2 3 4
python3 experiments/kws_conv.py --out /tmp/kws_conv
python3 experiments/kws_report.py /tmp/kws_ridge /tmp/kws_conv
```

Nothing was written to `results/` or `LEADERBOARD.md`; `docs/frontier.png` was
not regenerated. These are not CIFAR-10 points and do not belong on that board.

## The bug that ate the first sweep

Worth a section, because it is the kind of thing this project has been burned by
and because the fix is now a gate rather than a memory.

The first sweep came back non-monotonic in bit width. At 16 frames and 8 mel
bands the 3-bit artifact scored **8.10%** against a 8.33% chance line, while the
2-bit one beside it scored 21.94% and the 4-bit one 38.53%. Every 3-bit row in
that sweep sat at chance. That reads as a quantizer failure, and I diagnosed it
as one — a global Lloyd-max codebook spending its centroids on an outlying bias
row.

It was not. `pack_indices` packed `8 // bits` codes per byte, which is correct
for the widths that divide 8 and silently wrong for the ones that do not. At
3 bits it wasted two bits per byte and produced a layout the decoder does not
read. The artifacts were shipping noise and running perfectly. Nothing in the
harness could catch it: a self-contained numpy program that returns
well-formed labels from garbage weights passes every check the sandbox makes.

**Those three figures are from the superseded pre-fix run** and are the only
numbers in this memo that no current script reproduces — the code that produced
them no longer exists. What is reproducible is the cause. `check_roundtrip`
unpacks the shipped payload with the shipped expression and demands the original
indices back, on every artifact emitted:

`tests/test_kws_pack.py` pins it at all five widths, and — the part that
matters — pins that it **fires**, including on the original defect
reconstructed byte for byte (`test_gate_rejects_the_original_bug`). A gate that
has only ever been run against correct input has not been tested, and this
project has shipped a detector that passed against a deliberately broken
implementation before. The suite goes 43 to 64 passing; the CIFAR path is
untouched.

The wrong diagnosis is also on the record. Splitting the bias out of the
codebook, which is what I built while believing the quantizer was at fault,
turns out **not to be resolved**. Across the sixteen points where both arms were
measured after the packing fix, splitting the bias is worth **+1.20 pp on
average with a 4.47 pp standard deviation**, winning 10 of 16 and ranging from
−4.68 to +12.62 pp — and it costs 83 B more on average, because the two arms
select different ridge penalties and so ship differently compressible weights.
A mean barely above this project's 1.06 pp noise floor, with a spread four times
it and a confounded size axis, is not a finding. Both paths are kept and flagged
in `kws_ridge.py`; neither is claimed to win, and every number elsewhere in this
memo is from the split-bias arm.

## What classifies, and at what size

### The float ceiling

Before spending effort on quantization it is worth knowing what there is to
recover. `experiments/kws_ceiling.py` fits the same ridge head in float. It
ships nothing and is not a Pareto point.

| front end | frames | bands | dim | val | test |
|---|---:|---:|---:|---:|---:|
| mel | 16 | 8 | 128 | 46.79% | 44.05% |
| mel | 16 | 12 | 192 | 49.07% | 47.28% |
| mel | 16 | 16 | 256 | 50.48% | 50.33% |
| mel | 16 | 20 | 320 | 51.90% | 50.49% |
| mel | 16 | 26 | 416 | 52.35% | 50.94% |
| mel | 32 | 8 | 256 | 45.80% | 44.54% |
| mel | 32 | 16 | 512 | 50.08% | 49.35% |
| mel | 32 | 26 | 832 | 51.88% | 51.33% |
| mel | 49 | 20 | 980 | 51.86% | 50.08% |
| oct | 16 | 26 | 416 | 51.23% | 50.31% |
| oct | 32 | 26 | 832 | 51.02% | 50.67% |

(`kws_ceiling.py` prints 33 rows — 15 mel, 15 octave and 3 envelope-only; these
are representative.)

**A linear head on log-mel saturates just above 52% on validation,** and it
saturates in *bands*, not in frames: going from 8 to 26 mel bands at 16 frames
buys 5.6 points and then stops, while going from 16 to 49 frames buys nothing at
any band count. Since the head costs `(dim + 1) x 12 x bits / 8`, the features
that would help are exactly the ones that cost the most. **Mel beats octave
spacing on all fifteen matched (frames, bands) pairs, by 1.59 pp on average.**
The individual margins run 0.41 to 3.80 pp, a third of them at or below this
project's 1.06 pp noise floor; fifteen out of fifteen in the same direction is
not noise.

This ceiling, not the front end, is the first thing the sub-kilobyte band on
this dataset runs into — which is why the conv family below exists.

### The measured frontier

Two families, both the repo's own. `kws_ridge.py` puts a quantized ridge head
straight on the log-mel map. `kws_conv.py` is the sub-4 KB CIFAR family with the
image swapped for a spectrogram: random 3x3 convolutional filters drawn from a
four-byte seed, rectified, pooled, ridge head on top — the filters cost a seed
however many there are, so only the head is real weight.

155 declared points — 120 ridge, 35 conv — all scored through the harness on all
4,890 test utterances, and all kept under `artifacts/kws-derisk/` as the
evidence behind the byte counts. The Pareto frontier of them, from
`experiments/kws_report.py /tmp/kws_ridge /tmp/kws_conv`:

Four things in that table are worth naming.

**Convolution beats a linear head at identical seed cost, again.** Finding 2 in
[what-to-try.md](what-to-try.md) — measured on CIFAR — transfers intact: the
conv family owns every frontier point above 650 B and reaches 60.90% where the
plain ridge ceiling on the same features is 52% *in float*. Structure over the
mel map is worth more than more mel map.

**And it loses below 660 B, for a source reason.** The conv decoder is 765-852 B
of `predict.py` against 380-483 B for plain ridge. Below about 650 B the extra
source costs more than the extra structure earns and the frontier reverts to the
linear family: the smallest conv artifact is 563 B at 16.26%, against ridge's
592 B at 24.23%. That is the repo's central sub-KB finding — source is the
artifact — showing up as a crossover rather than as a slogan.

**Octave spacing beats mel at the very bottom and loses at the top.** The
smallest artifact on the board, 436 B, uses octave-spaced bands, whose edge
formula is ten source bytes shorter than the mel one. At the float ceiling mel
wins on all fifteen matched pairs. At 436 B ten source bytes are worth more than
1.6 points; at 3 KB they are not.

**4 bits wins most of the frontier.** Eight of the thirteen frontier points are
4-bit, including every point above 1.1 KB, which matches finding 5 on CIFAR:
precision beats width at fixed bytes. Below a kilobyte it is mixed — the three
smallest points are 1- and 2-bit, because there the codebook's own float16
centroids are a visible fraction of the artifact.

## The MDL question

Sending the 4,890 test labels with no model at all costs

    4,890 x log2(12) / 8 = 2,191.3 B

and the split is near-balanced by construction, so the empirical entropy is
3.5847 bits/label and the empirical figure — 2,191.1 B — is within a byte of the
uniform one. The budget used below is 2,191 B, the uniform figure truncated,
matching the convention `findings.md` uses for CIFAR-10's 4,152 B.

Label cost is priced by `price_labels`, **imported** from
`experiments/class_scaling_report.py` rather than reimplemented: code
right/wrong at `H(acc)` bits, then which of the other eleven classes it was at
`log2(11)`. No fitted temperature, so nothing is tunable, and every verdict is
conservative in the direction of "the model does not pay".

**Nothing pays.** Across all 155 declared points the cheapest two-part total is
**2,592 B against a 2,191 B budget**, 401 B over, and it belongs to the smallest
artifact on the board rather than the most accurate one.

|---|---:|---:|---:|---:|---:|
| `kws-oct-F16-M8-1b` | 436 | 17.16% | 2,156 | **2,592** | +401 |
| `kwsc-F16-M16-p2-k4-4b` | 660 | 28.77% | 2,035 | 2,695 | +504 |
| `kwsc-F16-M16-p7-k2-2b` | 816 | 34.15% | 1,959 | 2,775 | +584 |

**The MDL board is short by 27 to 30 points over the whole sub-1.2 KB range, and
the deficit is flattest exactly where the artifacts are smallest.** It is not a
near miss at one size and a rout at another; it is a uniform wall, which means
it will not be closed by moving along this frontier. Above 2,189 B the
question stops being asked at all: any artifact over **2,189 B** exceeds the
budget on its own, before a single label is sent, so no accuracy — not even
100% — can buy it back.

For comparison, CIFAR-10's board has exactly one artifact that pays, by 241 B,
and it is the smallest one there too. The structure is the same; this dataset
lands on the wrong side of it.

## Where the published frontier actually is

All verified against primary sources, with the caveats that matter for a
byte-counting project. **Every published sub-150 KB KWS number is a parameter
count times an assumed bit width, not a measured artifact.**

**DS-CNN-S, "Hello Edge"** ([arXiv:1711.07128](https://ar5iv.labs.arxiv.org/html/1711.07128),
Table 5): **94.4% at 38.6 KB**, 12 classes. Two corrections to how that number is
usually quoted. It is Speech Commands **v0.01**, not v2 — the paper cites
`speech_commands_v0.01.tar.gz`. And 38.6 KB is not weights: the table caption
says "The memory required for storing the 8-bit weights **and activations** is
shown in the table". The paper gives no parameter count for DS-CNN-S. The ARM
`ML-KWS-for-MCU` repo is not a usable cross-check — its table is an image and
its caption says validation set.

**MLPerf Tiny KWS** ([arXiv:2106.07597](https://ar5iv.labs.arxiv.org/html/2106.07597)):
Speech Commands **v2**, 12 classes, DS-CNN. The commonly quoted 92.2% is the
paper's **float** figure; the paper's own next sentence is "The quantized
reference model demonstrated **91.6%** accuracy on the full test set". Table 1's
benchmark row is 90% at 52.5 KB. The real artifact is
`kws_ref_model.tflite` in `mlcommons/tiny`, **53,936 bytes** (MEASURED via the
GitHub API), which is the closest thing in this literature to a number
comparable to ours. So the defensible pairing is **91.6% @ 53,936 B int8**. The
"92.2% at 52.5 KB" that circulates mixes a float accuracy with a quantized size;
this memo does not use it.

One further wrinkle worth inheriting rather than repeating: MLPerf cites Hello
Edge for "38.6K parameters", but Hello Edge's 38.6 is **kilobytes of weights and
activations** and that paper states no parameter count at all. The architecture
in `keras_model.py` — one conv plus four separable blocks, 64 filters — is
nearer 25 K weights.

**Below 10 KB, and below a kilobyte.** The smallest claims are µNAS at 95.36%
with 19.2 K int8 parameters ([arXiv:2010.14246](https://arxiv.org/pdf/2010.14246),
Table 2), FastGRNN at 92.10% in 5.5 KB of weights, TinySpeech-Z at 92.4% with
2.7 K parameters (v0.01, and SparkNet notes it "has no public implementation"),
and SparkNet[C=4] at 82.3%/83.5% with **1,416 parameters**
([arXiv:2406.06634](https://arxiv.org/pdf/2406.06634), Table 4). The only paper
found that measured real flash occupancy with a compiler is MicroNets, whose
smallest KWS model is 163 KB.

**Nothing under a kilobyte is published, at any class count.** That was searched
for specifically and not found.

## Recommendation: NO-GO

Not because a criterion fired. Both passed, and the front-end result is a clean
positive. The reasons are what the numbers show.

**The closed-form family is forty points behind the published literature at
comparable size, and on CIFAR it was fifteen points ahead.** That inversion is
the decisive number. On CIFAR-10 this repo's 5.2 KB artifact beats Müksch et
al.'s 5.3 KB by 15 points, which is what makes that board worth competing on.
Here, SparkNet reports 83.5% on 12-class v2 with **1,416 parameters** — the
paper reports parameters, not bytes, and priced at one byte each, which is the
most generous reading available to it, that is 1.4 KB of weights before any
code. Against 44.29% for our 1,137 B artifact and 52.74% for our 2,525 B one.
TinySpeech-Z claims 92.4% at 2.7 K parameters, unreproduced. The reason is not
mysterious: a second of
speech in a mel map is far more amenable to a small *trained* convolutional net
than a 32x32 natural image is, so the gap that closed-form ridge and random
filters can cover on CIFAR is a chasm here.

Closing it means porting the trained-CNN-plus-QAT half of this repo to audio.
That is the expensive half, it is three weeks, and it is the half that already
loses to µNAS by six times the bytes on CIFAR. Entering this board is signing up
for that fight on ground where the deficit starts forty points wider.

**The MDL board is dead by a uniform 27 to 30 points.** On CIFAR exactly one
artifact pays for its own transmission — thin but alive, and it is the reason
the sub-KB band is where the interesting work is. Here nothing pays and the
deficit does not shrink anywhere along the frontier. The second scoreboard,
which is the one that makes the sub-kilobyte band *matter* rather than merely
exist, has no entry point on this dataset.

**The question is answered, and it is a memo.** How many bytes of DSP a keyword
spotter needs took half a day and has a clean number: 99, storing nothing,
because numpy owns the FFT and mel spacing is a formula. That result is
portable — it is a statement about lever C and about what the declared runtime
contains, not about speech — and it does not need three weeks of Speech Commands
to be true.

**A second dataset is a second point on a curve already drawn, not a new
question.** At roughly a kilobyte, CIFAR-10 buys 4.4x chance and Speech Commands
buys 4.9x. Every structural finding transferred without modification:
convolution beats a linear head at identical seed cost, precision beats width at
fixed bytes, source is the binding constraint below a kilobyte and shows up here
as the ~600 B crossover where the conv decoder stops paying for itself. Nothing
was learned about *description length* that CIFAR had not already taught. What
was learned is about audio front ends, and that is one table.

### The honest counterargument

There is a real one, and it should be on the record rather than argued away.
**Every published KWS number below 150 KB is a parameter count times an assumed
bit width.** Not one of them is a measured artifact that runs. This repo's
harness is the only thing in view that produces that number, and a paper that
shipped real byte counts across 1-50 KB on Speech Commands would be a genuine
contribution — the sub-kilobyte band on this dataset is empty, verified, and it
is empty partly because nobody has a way to measure it.

It still does not clear the bar, for two reasons. The contribution would be an
accounting correction — "published sizes understate real artifacts by roughly
2x" — which is already stated in this repo's README as a caveat on the CIFAR
frontier and does not become more true for being restated on audio. And
producing it requires the trained-CNN port anyway, because a benchmark whose
points top out at 61% against a literature at 92% is not a benchmark anyone will
use.

### What is worth taking

* **Lever C has a much larger dynamic range than CIFAR could show.** On CIFAR
  "anything a line of numpy generates costs nothing" was worth almost nothing in
  absolute terms, because the transform being generated was a block mean. Here
  the same principle is worth 1,020 B — the difference between a front end that
  consumes 4% of the label budget and one that consumes 55% of it before a
  single weight ships. The generalization: *the value of lever C scales with how much
  structure the transform has, and a fixed basis with a closed-form generator is
  the best case there is.* Worth adding to `what-to-try.md`.
* **`np.fft` is free budget nobody has spent.** The declared runtime contains
  more than this project has used. The DCT stem named as untested in
  `what-to-try.md` item 8 is `np.fft.rfft` of a reshaped block, at zero stored
  bytes, and this memo is evidence it would cost about forty source bytes on
  CIFAR too.
* **The ~600 B conv-decoder crossover puts a price on lever G.** The conv family
  owns every frontier point above 660 B and cannot enter the band below it: its
  smallest artifact is 563 B at 16.26%, against a ridge artifact at 592 B and
  24.23%. Eight accuracy points, lost to 393 B of un-golfed decoder source. That
  is not an estimate of what golfing is worth — it is a measurement of what not
  golfing costs, in the one band where it decides which family wins.
* **`check_roundtrip` should probably move into `tinycifar`.** A quantized
  artifact whose payload does not unpack to the codes that were fitted is a
  silent, plausible-looking failure, and it cost an hour here. It is eight lines
  and it belongs next to the size metric.

### Known weaknesses, stated rather than buried

* **The emitted decoder is not golfed.** The 3-bit unpacking path is
  `np.unpackbits(...).reshape(-1,3).astype(np.uint32)<<np.arange(3)...` — 161
  characters — because it is `golf.unpack_expr`'s general branch reused
  unmodified, and the conv decoder was transcribed from `conv_features.py`
  rather than rewritten for this shape. In the 1,024 B frontier artifact,
  `predict.py` is 846 B of 1,347 B raw: **source is 63% of it**, the same
  two-thirds the CIFAR sub-KB work found. On CIFAR, golfing that source was
  worth 116 B at this size. The lever is entirely unpulled here, so every byte
  count in this memo is an upper bound by perhaps 50-150 B. It does not move any
  verdict — the MDL gap is 401 B at its narrowest and 27 to 30 accuracy points
  everywhere — but it does mean the frontier table is not the frontier.
* **No quantization-aware training.** The CIFAR work found QAT is a
  precondition rather than a refinement — 18.55% against 77.52% at 3 bits. There
  is no backprop anywhere in this memo, so the gap between the float ceiling and
  the quantized artifacts is unaddressed by the one method known to close it.
  That gap is 5-15 points here.
* **`_unknown_` is a single class covering twenty words**, and it is the class
  every one of these models is worst at. No per-class breakdown is reported
  because none was computed; that is a real gap in the diagnosis.
* **One seed, one background-noise assignment.** The silence waveforms and the
  unknown sample are a fixed draw. Re-drawing them would move every number by
  some unmeasured amount.
* **The oblivious-table family was not tried.** It is what owns the 470-700 B
  band on CIFAR, and the smallest artifacts here are ridge heads, which is the
  family CIFAR found *cannot* enter that band. A 12-class table over thresholded
  mel bands is the obvious missing row and it was not run.
